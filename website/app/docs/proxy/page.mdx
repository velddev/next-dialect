# The proxy

A build leaves sentinel tokens where the messages go. Something has to put the
strings in. On a static host that happens once, on disk. On a server it happens
per request, and that is the proxy.

It is a Next proxy file, so `next build` and `next start` stay exactly as they
are and nothing about your deployment has to change to accommodate it.

## Mounting it

Create `proxy.ts` at the project root, next to `app/`:

```ts
import { createDialectProxy } from 'next-dialect/proxy'

export const proxy = createDialectProxy()

export const config = {
  matcher: '/((?!_next/image|favicon.ico).*)',
}
```

That is the whole integration. Do not exclude `_next/static` from the matcher —
that is where the localized chunks are, and the proxy has to see them. Next runs
proxy files before filesystem routes, so it gets the asset request first and
passes through anything that carries no messages.

`createDialectProxy()` reads what `withDialect` published to the environment.
If your platform evaluates `next.config` only at build time, pass the settings
instead:

```ts
export const proxy = createDialectProxy({
  locales: ['en', 'nl'],
  defaultLocale: 'en',
})
```

It needs the Node.js runtime, because it reads catalogs and chunks from disk.
Proxy files use Node by default in Next 16; on 15.5 or newer the same code works
as `middleware.ts` with the Node runtime opted in.

## What it does on the first request

The proxy scans the emitted `.js` and `.css` files once and records which of
them actually contain message tokens. Everything else is left alone forever.
That set is small — it is the chunks holding your components' text, not your
dependencies — and it is the difference between a locale switch costing
kilobytes and costing megabytes.

The alternative, forking the whole output tree per locale, is what the static
path has to do, and it is worth seeing why this one does not: duplicating the
tree makes React, the framework and every vendor chunk locale-specific, even
though not one of them contains a string. A visitor switching language would
re-download the entire application.

## Serving a localized chunk

Chunk URLs are built by the webpack runtime in the browser, which knows nothing
about locales, so the locale cannot be in the path. A chunk that carries
messages is therefore resolved from the locale cookie and served with
`Vary: Cookie`, so caches keep one entry per locale rather than serving Dutch to
an English reader.

A chunk with no tokens in it never enters this path — it is passed straight
through to Next, with one URL and one cache entry for every locale. That is the
majority of your bundle.

Substituted chunks are cached in memory, raw and gzipped, keyed by locale and
file. They are immutable for that pair, so compressing once is free after the
first hit, and they carry a one-year `immutable` cache header.

## Negotiating a locale

An un-prefixed URL resolves in this order:

1. the locale cookie, if it names a locale you ship;
2. `Accept-Language`, matched first exactly, then by base language, unless
   `detection.acceptLanguage` is off;
3. the default locale.

What happens next depends on `localePrefix`. With `'always'`, the visitor is
redirected to the prefixed URL. With `'as-needed'`, the default locale is served
at the canonical un-prefixed URL, and a request for its prefixed form is
permanently redirected back to the short one.

Either way the resolved locale is written back to the cookie — including when a
visitor lands directly on a prefixed URL, so that the chunks the page is about
to request resolve to the locale it is actually rendering.

Shared assets never enter negotiation. They have no locale to negotiate.

## The static path

`next-dialect build` with `output: 'export'` uses the same substitution code
with no server involved. Every text file in the export is rewritten per locale
into `dist/<locale>/`, asset URLs are prefixed wholesale, and each locale ends
up a complete, self-contained site. The build fails rather than shipping a page
with an unreplaced token in it.

Duplication is the price of having no request-time hook at all.

## Known limits

- Localized chunks vary on `Cookie` rather than carrying the locale in their
  URL, which is a coarser cache key than a locale-scoped path would be.
- The Node.js runtime is required, so Next 16, or 15.5 with `middleware.ts`
  opted into Node.
- Localized chunks keep their original content hash, so their source maps drift
  once strings are substituted. Next disables production browser source maps by
  default, which makes this inert unless you turn them on.
